# UAV Fleet Telemetry — Backend + Dashboard

A working backend and live dashboard that stores battery health (SoC, SoH,
voltage, current, temperature) and vibration data from multiple UAVs, each
keyed by its own `uav_id`. Built for a UAV project that also includes a BMS
and fleet-management/flight-planner component — this is the data-storage
and monitoring layer that ties them together.

## What's in here

```

├── backend/

│   ├── requirements.txt
```

## 1. Run it locally

```bash
cd backend
pip install -r requirements.txt
uvicorn main:app --host 0.0.0.0 --port 8000 --reload
```

Open **http://localhost:8000** — that's the dashboard. It'll show "No UAVs
registered yet" until data comes in.

## 2. Send it some test data

In a second terminal, from the project root:

```bash
pip install requests
python simulate_uav.py --uavs UAV-01 UAV-02 UAV-03 --interval 2
```

This simulates a 3-drone fleet discharging batteries over a flight, with
realistic vibration noise. Watch the dashboard update live — click a UAV in
the left panel to see its charts.

## 3. API reference

| Method | Endpoint                          | Purpose                              |
|--------|------------------------------------|---------------------------------------|
| POST   | `/api/uavs/register`               | Register/update a UAV's name & model |
| GET    | `/api/uavs`                        | List all UAVs + their latest reading |
| POST   | `/api/uavs/{uav_id}/telemetry`     | Push one telemetry reading            |
| GET    | `/api/uavs/{uav_id}/telemetry`     | Get history (default last 200 rows)  |
| GET    | `/api/uavs/{uav_id}/latest`        | Get just the latest reading           |
| DELETE | `/api/uavs/{uav_id}`               | Remove a UAV and its history          |

Interactive API docs (auto-generated by FastAPI) are at
**http://localhost:8000/docs** once the server is running.

### Telemetry payload fields

All fields are optional except that you POST *something* — send whatever
your sensors currently give you, and add more fields later without breaking
anything.

```json
{
  "timestamp": "2026-07-18T10:15:00Z",
  "battery_voltage": 22.4,
  "current": 9.1,
  "soc": 78.5,
  "soh": 96.2,
  "temperature": 31.4,
  "vibration_x": 0.06,
  "vibration_y": 0.05,
  "vibration_z": 0.09,
  "altitude": 42.0,
  "latitude": 8.5241,
  "longitude": 76.9366
}
```

`vibration_rms` is computed automatically on the backend from x/y/z — you
don't need to send it.

## 4. Connecting a real UAV (Raspberry Pi / BMS microcontroller)

On the companion computer (e.g. a Pi reading MAVLink telemetry + a BMS board
over I2C/UART), send a POST request after every reading cycle:

```python
import requests
from datetime import datetime, timezone

BACKEND_URL = "http://<your-server-ip>:8000"
UAV_ID = "UAV-01"

def send_telemetry(bms_reading, vibration_reading):
    payload = {
        "timestamp": datetime.now(timezone.utc).isoformat(),
        "battery_voltage": bms_reading["voltage"],
        "current": bms_reading["current"],
        "soc": bms_reading["soc"],
        "soh": bms_reading["soh"],
        "temperature": bms_reading["temp"],
        "vibration_x": vibration_reading["x"],
        "vibration_y": vibration_reading["y"],
        "vibration_z": vibration_reading["z"],
    }
    requests.post(f"{BACKEND_URL}/api/uavs/{UAV_ID}/telemetry", json=payload, timeout=5)
```

Call this every 1–5 seconds during flight, and once more right after landing
to capture the final post-flight reading.

**Networking note:** for this to work, the backend needs to be reachable
from wherever the drone's companion computer has connectivity — either a
local Wi-Fi/4G hotspot at the flying site, or deploy the backend to a small
cloud VM (Render, Railway, a $5 DigitalOcean droplet, etc.) so it's reachable
from anywhere. If you deploy it remotely, swap SQLite for PostgreSQL for
better concurrent-write handling — SQLAlchemy makes that a one-line change
to the `engine` connection string in `main.py`.

## 5. Feeding this into your ML/post-flight analysis phase

Every row in the `telemetry` table is timestamped and tagged by `uav_id`,
so pulling a flight's history for model training is a single query:

```python
import requests
import pandas as pd

rows = requests.get("http://localhost:8000/api/uavs/UAV-01/telemetry?limit=5000").json()
df = pd.DataFrame(rows)
df.to_csv("uav01_flight_log.csv", index=False)
```

From there you're straight into feature engineering — e.g. discharge-curve
slope for SoH prediction, or vibration_rms spikes for anomaly detection —
feeding the model-training phase of your project.

## 6. Safety alerts and automatic Return-to-Launch

The backend now evaluates every incoming reading against thresholds defined
in `THRESHOLDS` at the top of `main.py`:

```python
THRESHOLDS = {
    "soc_critical": 20.0,        # % battery -- below this, RTL is triggered
    "soc_warning": 35.0,
    "temp_critical": 60.0,       # deg C
    "temp_warning": 50.0,
    "vibration_critical": 0.30,  # RMS
    "vibration_warning": 0.20,
}
```

Tune these once you've flown a few real flights and know your normal ranges.

**What happens on a critical reading:**
- The dashboard shows a red alert banner with the specific reason(s).
- The backend sets that UAV's `pending_command` to `"RTL"`.
- The Jetson's `pixhawk_bridge.py` polls for this every cycle and, when it
  sees `RTL`, sends an actual `MAV_CMD_NAV_RETURN_TO_LAUNCH` command to the
  Pixhawk over MAVLink.
- An operator can also manually trigger **Force Return to Base** or **Force
  Hold Position** from the dashboard at any time, or **Clear Command** to
  cancel a pending one.

**Important safety note:** this is a *software-layer* safety net that
depends on network connectivity between the Jetson and the backend. For
real flights, configure ArduPilot's own failsafes as your primary
protection (`BATT_FS_LOW_ACT`, `FS_EKF_ACTION`, etc. in Mission Planner /
QGroundControl) — those trigger onboard, instantly, with zero dependency on
Wi-Fi/4G. Treat this backend-driven RTL as a secondary layer, valuable for
things the flight controller doesn't watch by default (like a fleet-wide
custom vibration or temperature threshold), not a replacement for onboard
failsafes.

## 7. Scaling to a real multi-drone fleet

Nothing here needs to change to go from 1 to 5 drones — each drone just
needs its own `uav_id` and hits the same backend URL. The dashboard's fleet
panel already lists every UAV that's ever POSTed data, side by side.
